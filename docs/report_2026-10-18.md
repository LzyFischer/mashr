# MAS-HR 实验报告：两个时间尺度的组织学习

> 2026-10-18。数据来自 `results/rsi/gsm8k_r1/`（第一版，GSM8K）和 `results/orgrsi/math_hand/`、`results/orgrsi/math_found/`（当前版本，MATH）。所有数字都可以从这些目录里的 `log.txt`、`trace.json`、`test.json` 和每轮的 `report.md` 查到。

---

## 0. 摘要

1. **RSI 能在接近完整团队正确率的前提下大幅降成本。** MATH Level 4–5（整数答案）的 test 集共 156 题。完整团队 98.1%、每题 26877 token。从 27B 成立的组织出发，经过 5 轮 RSI 后为 94.9%、6629 token，成本降到完整团队的 25%；从手写组织出发为 94.2%、7929 token，成本降到 30%。
2. **"成立公司"这一步贡献最大。** 27B 只读了 30 道题，设计出的组织在 RSI 之前就达到 95.5%、成本 37%，比手写组织经过 5 轮 RSI 还好。之后的 RSI 主要在降成本：再降 34%，正确率基本不变（少对 1 题）。
3. **RSI 做出了可解释的组织决策。** 两组各开掉了一个员工（solver_A、几何专员 geom），都没有招人。两组都把 HR 的"每题指导"关掉了（手册里写着 guide 必须为空），也都把 SOP 合并成了"先做，出状况再升级"的结构。在 GSM8K 上，RSI 也自己学会了不让 HR 自己答题。
4. **test 上没守住正确率约束。** 约束是"比完整团队最多低 2 个点"，dev-B 上满足了，但两组最终在 test 上都低了 3–4 个点。最可能的原因是在同一个 200 题的 dev-B 上反复挑 15 个候选，挑出的赢家带有运气成分。
5. **技能库在过拟合。** RSI 新增的技能里，有不少是针对个别 dev 错题写的解法备忘，比如 `complex_equilateral`、`roots_unity_count`。每个员工平均挂了 11–14 项技能，HR 的 prompt 从约 3000 字符涨到 7000–10000 字符。这和"技能放在员工那里、手册保持简短"的设计初衷相反。
6. **归因给出了清楚的员工级证据。** 在 team SOP 里，critic 是唯一不可或缺的人：去掉他，31 次中有 16 次会答错。两个并行的 solver 互为冗余，去掉任何一个，几乎都不影响结果。review 阶段改了 23 次答案，13 次改对、0 次改错。single SOP 里"没把握才叫 reviewer"这一步，81 次只触发了 2 次，因为员工几乎总说自己有把握，这个升级信号基本不起作用。

## 1. 系统

### 1.1 两个时间尺度

| | 快回路（每题，在线） | 慢回路（每个数据集，离线） |
|---|---|---|
| 谁 | HR：Qwen3.5-9B，不开 thinking | 顾问：Qwen3.8-27B，开 thinking |
| 输入 | HR 手册 + 题目 | 当前组织 + 绩效报告 + 之前每轮的尝试记录 |
| 输出 | 一份结构化方案：SOP、每个阶段派谁、thinking 档位、开启哪些技能、每人一句指导 | 一组编辑操作，修改组织 |
| 调用次数 | 每题 1 次 | 每轮 3 个候选，每个最多修复 1 次 |

### 1.2 组织（`mashr/org.py`）

| 组成 | 内容 | HR 是否可见 |
|---|---|---|
| 花名册 staff | 每人一份岗位说明 + 自己掌握的技能 ID | 可见 |
| 离职池 alumni | 被开掉的员工，可以复职 | **不可见**。手册里提到离职员工会被校验拒绝 |
| 技能库 skills | ID → 一段具体做法（≤600 字符） | 只看到 ID 和简介 |
| SOP 库 | 若干阶段，每个阶段有任务类型（solve / review / decide）、触发条件 when、能看到哪些前序阶段 sees、对后续阶段展示完整内容还是只展示答案 show | 可见 |
| HR 手册 handbook | 派工规则 | 可见 |
| 默认方案 | HR 输出不合法时使用 | — |

**触发条件**由规则引擎判断，不需要再调用 HR：`always`、`disagree:<阶段>`（两人以上答案不同）、`unsure:<阶段>`（有人自报 low confidence 或没给出答案）、`missing:<阶段>`、`long:<阶段>:<token 数>`。

**"开人"和"这题不用"的区别：** "这题不用"是 HR 在现有选项里做选择；"开人"是 RSI 把这个选项从 HR 眼前拿掉。

### 1.3 RSI 每一轮（`mashr/orgrsi.py`）

1. 用当前组织跑一遍 dev-A，生成绩效报告，内容包括：
   - 总体结果，以及按"学科 × 级别"分组的结果
   - 每个 SOP 阶段多常被触发、有没有改变答案、改对还是改错
   - **leave-one-out 归因**：在最多 60 道多人参与的题上，把某个员工从某个阶段去掉重跑，统计"去掉就答错"（needed）和"去掉反而答对"（harmful）的次数。没变的部分直接走缓存，所以很便宜
   - HR 的使用情况：派了谁、开了哪些技能、写了多少指导、不合法输出的原因
   - "省错了"的题（组织答错、完整团队答对），以及花费最高的答对题
2. 27B 提出 3 组编辑操作，共 12 种：招人、开人、复职、改岗位说明、设置员工技能、增 / 改 / 删技能、增改 / 删 SOP、改手册、改默认方案。校验不通过时把错误发回去修一次。
3. 门控：在 dev-B 上实测。正确率 ≥ 完整团队 − 2 个点才算合格；合格的候选里选成本最低的，而且要比当前组织更好才接受。还没有合格的候选时，先接受正确率最高的。
4. 第 0 轮可以用手写组织（`--init hand`），也可以让 27B 读 30 道 dev-A 题后成立公司（`--init found`）。

第一版的 Verifier（让 27B 预判候选会不会掉点）已经去掉。在 GSM8K 上，15 个候选里它刷掉了 12 个，其中包括第 2、3、5 轮最终被接受的候选（这三轮它把 3 个候选全部刷掉，靠"全部被刷掉就都送去实测"的兜底才得以评估）。它的判断和实测结果几乎不相关。

## 2. 实验设置

| 项目 | 设置 |
|---|---|
| 员工和 HR | Qwen3.5-9B（Tinker），温度 0.6 |
| 顾问 | Qwen3.8-27B（Tinker），thinking 开 |
| thinking 档位 | off；low = 最多约 1024 推理 token；high = 最多约 4096。超出预算就强制结束推理、直接作答 |
| 成本 | 生成 token + 0.25 × prompt token，包含 HR 的调用 |
| 完整团队（参照） | 3 个 solver 独立求解 → 3 个 solver + critic 互评 → judge 决定，除 judge 外都开 low |
| MATH 数据 | MATH Level 4–5 中答案为整数的题，可直接按整数判分。dev-A 150 题、dev-B 200 题，从 train 按固定 seed 抽取；test 是 MATH500 中所有符合条件的 156 题，其中 Level 5 有 74 题 |
| 轮数 | 5 轮，每轮 3 个候选；ε = 2 个点 |
| 用时 | 两组并行，约 50 分钟 |

**统计精度：** test 只有 156 题，95% 正确率附近的标准误约 ±1.7 个点。dev-B 200 题，约 ±1.5 个点。下文所有小于 2 个点的差距都应视为噪声。

## 3. MATH 主实验

### 3.1 test 结果

| | 正确率 | Level 5 | 每题成本 | 占完整团队 |
|---|---|---|---|---|
| 完整团队 | **98.1%** | 97.3% | 26877 | 100% |
| 手写组织（第 0 轮） | 87.8% | 86.5% | 10850 | 40% |
| 手写组织 + 5 轮 RSI | 94.2% | 93.2% | 7929 | 30% |
| 27B 成立的组织（第 0 轮） | 95.5% | 94.6% | 10001 | 37% |
| 27B 成立的组织 + 5 轮 RSI | 94.9% | 93.2% | **6629** | **25%** |

### 3.2 每轮被接受的组织（dev-B；完整团队 94.5%，合格线 92.5%）

| 轮次 | 手写组：正确率 / 成本 | 27B 组：正确率 / 成本 |
|---|---|---|
| 0 | 89.5% / 12223 | 90.0% / 11069 |
| 1 | 92.5% / 13391 | 94.0% / 10463 |
| 2 | 95.0% / 11323 | 94.0% / 8809 |
| 3 | 94.0% / 8480 | 95.0% / 8323 |
| 4 | 不变 | 93.0% / 7082 |
| 5 | 不变 | 不变 |

两组都是先把正确率拉过合格线，再连续压成本。最后 1–2 轮没有找到更好的候选。

### 3.3 组织的变化

| | 手写组：第 0 轮 → 最终 | 27B 组：第 0 轮 → 最终 |
|---|---|---|
| 员工 | 5 → 4（开掉 solver_A） | 7 → 6（开掉 geom） |
| 技能库 | 4 → 19 | 27 → 29 |
| 每人平均技能数 | 1.4 → 13.8 | 9.3 → 11.5 |
| SOP | 4 → 4（重写） | 5 → 2 |
| HR prompt 长度（字符） | 3074 → 7090 | 10669 → 9696 |

**27B 组最终的两个 SOP：**
- `single`：一人起草 → 没把握或没答案时叫 reviewer → reviewer 也没把握时叫 judge
- `team`：两个专员并行 → 有分歧或没把握时叫 critic 复核 → critic 没把握时叫 judge

**手册里的派工规则：** 只看题面关键词。图形、优化、多项式、矩阵、复数、计数、模运算等用 team，按题型配专员，比如有图形题就必须派 careful，计数题必须派 counter。只有一步运算或简单的单知识点题才用 single。

### 3.4 归因证据（27B 组第 5 轮报告，dev-A）

| 员工 | 在阶段中出现的次数 | needed | harmful | 无影响 |
|---|---|---|---|---|
| critic | 31 | **16** | 0 | 15 |
| judge | 9 | 3 | 0 | 6 |
| careful | 33 | 3 | 1 | 29 |
| algebra | 46 | 1 | 2 | 43 |
| counter | 31 | 1 | 0 | 30 |

| 阶段 | 被选中 | 实际触发 | 改变答案 | 改对 | 改错 |
|---|---|---|---|---|---|
| team.review | 69 | 31 | 23 | 13 | 0 |
| team.decide | 69 | 10 | 10 | 3 | 0 |
| single.check | 81 | **2** | 1 | 0 | 0 |
| single.decide | 81 | 0 | 0 | 0 | 0 |

**解读：**
- team 里的价值集中在 critic：答案有分歧时，靠他裁决。两个并行 solver 中的任何一个单独去掉影响都很小，所以理论上可以只保留"一个 solver + 一个 critic"。
- single 的升级通道基本不起作用：员工几乎总是报告 high confidence，`unsure` 很少触发。所以 single 实际上就等于单人作答，它的错误没有任何检查。

## 4. GSM8K 先导实验（第一版）

第一版只有 5 个固定员工，RSI 只能改 HR 的"人事规则"文本，还带着 Verifier。数据：dev-A、dev-B 各 200 题，取自 train；test 是 test 集前 300 题。

| test | 正确率 | 每题成本 | 占完整团队 |
|---|---|---|---|
| 完整团队 | 97.0% | 13655 | 100% |
| HR 第 0 轮 | 75.3% | 1494 | 11% |
| HR + 5 轮 RSI | 96.3% | 3110 | 23% |

- 第 0 轮 HR 有约 30% 的题选择自己答，正确率因此只有 75%。RSI 在第 2 轮写出"Never use self"。
- **局限：** 在 GSM8K test 前 200 题上，单个 solver 关掉 thinking 就有 95%，成本约 225 token。所以 GSM8K 不适合检验"按题调配"有没有价值，这也是改用 MATH 的原因。
- 这次运行里有一个解析器 bug：HR 把模板名写进了 `mode`，2–6% 的题因此回退到完整团队。另外当时缓存层还没有并发去重。两者对结论的影响都很小，但数字会略有偏差。

## 5. 问题与局限

1. **门控选择偏差，test 上没守住约束。** 每组 5 轮共在同一个 dev-B 上比较 15 个候选，被接受的组织有的刚好压线，比如 27B 组第 4 轮是 93.0%，合格线 92.5%。改进方向：扩大 dev-B；用配对检验代替点估计；保留一个只在最后使用一次的 holdout 来决定最终版本。
2. **技能过拟合和 prompt 膨胀。** 需要加约束：限制每个员工的技能数，比如 ≤5；新技能必须在多道 dev 题上起过作用；技能长期没人开启就删除。也可以把 HR 的 prompt 长度明确写进目标。
3. **自报置信度这个信号无效。** `unsure` 几乎不触发。需要更可靠、又不花钱的信号，比如让同一个员工做一次便宜的自检、用 Python 代回验证、输出长度等，或者干脆让 single 也默认有一次低成本复核。
4. **HR 输出不合法的情况还在。** MATH 上占 dev-B 的 1–7%，主要原因是 9B 把不同 SOP 的阶段名混用。现在按顺序映射兜底，但手册越长，问题越多。
5. **缺少关键对照。** 这次没有跑单个 solver（各档 thinking）和"最佳固定配置"，所以还不能回答"按题调配是否优于一个开 thinking 的单人"。这在 MATH 上很可能不成立，是下一步必须补的实验。
6. **可复现性。** Tinker 固定 seed 也不保证输出完全一致。现在靠缓存保证同一个调用只采样一次，但同样的配置重新跑一遍，结果仍可能有 1–2 个点的波动。目前每组只有一个种子。

---

## 6. 下一步（建议顺序）

1. 补对照实验：单 solver（off / low / high）、最佳固定配置、"一个 solver + 一个 critic"。
2. 修技能过拟合：加上技能数上限、跨题证据要求和自动清理。
3. 门控改为配对检验，dev-B 扩到 400–500 题，加 holdout。
4. 换掉无效的 `unsure` 信号，比如代回验证或低成本自检。
5. 消融实验：有 / 无归因、有 / 无"成立公司"、"开人"vs"用规则禁用"。
6. 多个种子；跨数据集迁移，比如把 MATH 上学到的组织直接用在 OlympiadBench 上。

## 7. 复现

```
cd ~/project/mas-hr
P=~/miniconda3/envs/tinker/bin/python
set -a; source ~/.config/hrsi/tinker.env; set +a
bash results/orgrsi/run_math.sh                              # 第 3 节，两组
$P -m mashr.rsi --rounds 5 --k 3 --out results/rsi/gsm8k_r1   # 第 4 节，第一版
```

命中缓存的调用不花钱。缓存在 `results/mashr/cache.sqlite`。
